# CLAUDE.md（ユーザーグローバル設定）

## コミュニケーション

- 日本語で応答する。技術用語・固有名詞は、その分野の日本語話者がふだん使う表記（多くはカタカナ語か英語のまま）で書く。和語や漢字 1 字に訳さない
  - 避ける例: 枝（ブランチ）、殻（シェル）、窓（ウィンドウ）、糸（スレッド）、写し（コピー）、控え（バックアップ）、字体（フォント）、台本（スクリプト）、道具（ツール）、部品（コンポーネント）、試験（テスト）、札・知らせ（バッジ・通知）、分身（サブエージェント）
  - 定着した漢語を和語の名詞にしない（確認 → ×確かめ、監視 → ×見張り）。動詞の「確かめる」は使ってよい
- 結論を先に書き、判断には根拠を添える
- 作業の報告は、冒頭で完了状況（済み・進行中・未着手）とユーザーに残っている作業を示す

## 作業の進め方

- 不可逆な変更（コミットしていない内容の削除・上書き、強制 push・公開済みの履歴の書き換え、リモートのブランチ・タグ・リリースの削除、本番環境への変更、外部送信など）は、トレードオフを示して判断を仰ぐ。それ以外の後から戻せる操作（コミット、作業ブランチの push、PR の作成・マージなど）は、指示を待たずに推奨の方針で進め、問題があれば revert などで戻す。要件が曖昧なとき・実装方針が複数あるとき・想定外の状況のときも、推奨値で進める
  - 推奨を決められる判断は、選択式の質問（AskUserQuestion）にしない。推奨で進め、報告に「選択肢・選んだもの・根拠・戻し方」を書く。質問するのは、不可逆な変更の判断と、推奨を決められない（利用者の好み・外部の事情で決まる）ときだけ
  - 可逆な更新は承認を求めない。例: 導入済みのスキル・スクリプトのコピーの更新（マージ済みの正本から）、配布先への PR の作成、作業ブランチの push・PR のマージ、ローカルの設定ファイル（防御設定を除く）の追記。問題が出たら、revert やコピーし直しで戻す
  - 可逆な操作で Bash の権限の確認（ask）が出たときは、その場では確認に任せ、報告で settings.json の allow に足すコマンドのパターンを提案する（防御設定の編集は「外部リソース・拡張機能・防御設定の安全規則」に従う）
- 判断が発生したら、検討した選択肢をすべて（選ばなかったものも含めて）挙げ、どれを選んだかと、選んだ根拠を明示する
- エラーは原因を報告してから直す。`--force`・エラーの握りつぶしなど、症状だけを消す回避はしない
- 「完了した」「テストが通った」と報告する前に、最後の編集の後で検証コマンド（テスト・ビルド・lint など）を実行し直し、コマンドと終了コード（または出力の末尾数行）を報告に書く。実行できなかった検証は「未検証」と明記し、部分完了として報告する。完了前の点検手順は `verify-done` スキル

### トークン経済性

- 結果が同等なら、トークン消費が少ない手段を選び、その旨を明示する。反復処理・大量出力・多数のプロセス起動を伴うものは、スクリプトにまとめて独立実行する（またはユーザーに起動を頼む）。大量のログはファイルに書き出し、要約や抜粋だけを読む
- 節約すると質や確実性が下がる場合は、自分で決めずに選択肢を示す。節約を理由に検証を省かない

### コンテナ: `docker` → `podman`

- Docker CLI は入れていない。手順書の `docker ...` は `podman ...` に読み替える（`docker` は settings.json の deny 設定でブロック済み）。`docker-compose` は Podman Desktop に同梱されているので、そのまま使える
- イメージ名は完全修飾で書く（例: `docker.io/library/nginx:latest`）。rootless が既定なので、権限エラーを `sudo` で回避しない
- deny パターンのせいで、`wsl.exe ... grep docker` のように**末尾が ` docker` になるコマンド**もブロックされる。`'docker'` と引用符で囲めば通る

## セキュリティ

- 本番データをテスト環境で使わない（必要ならマスキング・仮名化する）
- 本番環境への変更・デプロイは明示的な承認を得てから行う。`production` / `prod` / `prd` を含む設定や接続先を操作する前には確認する

## Git

- 可逆な変更を戻しやすくするため、適切な粒度でコミットする（1 コミットに 1 つの目的。無関係な変更を混ぜない）
- `git push`・PR の作成・PR のマージは、自動で行う（可逆なので、問題があれば revert で戻す）。既定のブランチにいるときは、作業ブランチを切って PR を作り、CI が通ってからマージする
- push の前に `gitleaks` で秘密情報が含まれていないか確かめる。公開された内容は revert しても消えない
- 次は不可逆なので、トレードオフを示して判断を仰ぐ: 強制 push（`--force` / `--force-with-lease`）、リモートのブランチ・タグの削除（マージ済みの自分の作業ブランチを除く）、自分のものではないリポジトリ（フォーク元など）への push・PR の作成・マージ
- `--no-verify` は明示的な指示があるときだけ使う
- 改行コードを `core.autocrlf` の設定に左右させないため、リポジトリには `.gitattributes` を置く。ひな形は `python ~/.claude/scripts/check-encoding.py --gitattributes <リポジトリ>`（そのリポジトリにある形式の行だけが出る。形式ごとの要件と根拠は同スクリプトの `RULES`）。新しく作るリポジトリでは作成し、既存のリポジトリで無い・足りないときは提案する（`git add --renormalize .` の差分が共同作業者にも及ぶため、正規化は単独のコミットにする）
