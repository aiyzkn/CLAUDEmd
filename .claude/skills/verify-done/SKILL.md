# /verify-done — 完了報告の前の点検

「完了した」「テストが通った」という報告を、自己申告ではなく**証拠**にもとづいて行うための点検手順。よくある失敗は、テストが通った後に編集を続け、再実行しないまま「すべて通過」と報告すること。だから検証は**最後の編集の後**に実行し直す。

## 手順

### 1. 差分を確かめる

```bash
git status --short && git diff --stat HEAD
```

- 依頼と無関係なファイルが変わっていないか（あれば理由を説明できるか）
- 生成物・一時ファイル・秘密情報（`.env`、鍵、トークン）が混ざっていないか
- git 管理外なら、このセッションで編集したファイルの一覧で代える

### 2. 検証コマンドを決める

引数で渡されたらそれを使う。無ければ、プロジェクトの定義から選ぶ（推測で作らない）:

| 手がかり | 候補 |
|---|---|
| `package.json` の `scripts` | `test`・`lint`・`typecheck`・`build` |
| `Cargo.toml` | `cargo test`・`cargo clippy`・`cargo build` |
| `pyproject.toml` / `pytest.ini` | `python -m pytest`・ruff / mypy の設定があればそれも |
| `Makefile` / `justfile` | `test`・`check` ターゲット |
| `.github/workflows/*` | CI で実行しているコマンド（ローカルで再現できる範囲） |
| CLAUDE.md・README | 記載されたテスト・ビルド手順 |

フック・設定ファイルなら、`hook-test` スキルや構文検査（`python -m json.tool`、`bash -n`、`check-encoding.py`）を検証として使う。文書・設定だけの変更で検証コマンドが無い場合は「該当なし」とし、代わりに何を見て確かめたかを書く。

### 3. 最後の編集の後で実行し直す

- 出力が長くなるコマンドはファイルに書き出し、終了コードと末尾だけを読む（`> log 2>&1; echo "exit=$?"; tail -n 20 log`）
- 失敗したら、完了報告ではなく原因の報告に切り替える。テストを消す・skip にする・期待値を書き換えて通すことはしない（仕様変更として正しい場合は、その理由を報告に書く）
- 時間がかかりすぎて実行できない場合は、`long-run` スキルを使うか、「未検証」として扱う

### 4. 残り物を探す

追加した行だけを対象にする:

```bash
git diff -U0 HEAD | grep -nE '^\+.*(TODO|FIXME|XXX|WIP|console\.log|print\(|dbg!|debugger)' || echo "なし"
```

見つかったものは、意図して残すか消すかを判断し、残す場合は報告に書く。

### 5. 報告を突き合わせる

- サブエージェント・ワークフローの「完了」「通った」は、ツールの実行結果（実行したコマンドと出力）で裏付けが取れるものだけを採る
- 依頼に複数の要件があったなら、要件ごとに済み・未済を確かめる

## 報告の形

```markdown
**状況: 完了**（または **部分完了** / **未完了**）
残作業（ユーザー）: なし（または `git push` など）

- 変更: <git diff --stat の要約>
- 検証: `<コマンド>` → exit 0（最後の編集の後に実行）
  ```
  <出力の末尾数行>
  ```
- 未検証: <なし／内容と理由>
- 残したもの: <なし／TODO などとその理由>
```

1 つでも未検証や失敗が残っていれば「完了」と書かず、「部分完了」として何が残っているかを先に書く。
